# Scenario process: current flow and review points

CAPEX category, optional lower categories, search depth and DOE are independent choices. Medium may include Zero; High may include Zero and Medium independently. The default is unchecked. Proposals are evaluated together against the original source, not added as percentages or efficiencies from separate category cards. A repeated equipment/parameter uses the current category target, then the highest included lower category; search never writes two conflicting targets to one parameter.

## Intervention definitions shared by code and Gemini

| Category / cost | Intervention | Reliability evidence |
|---|---|---|
| Zero CAPEX / existing resources | Operating settings and work practices within installed capacity | OPERATIONAL: explicit MTBF/MTTR targets supported by history or trials. |
| Zero capital / additional OPEX | Additional maintenance, repair staffing or spares | MAINTENANCE: disclose recurring cost; do not call it free or Medium CAPEX. |
| Medium CAPEX | Local retrofit, component rehabilitation or monitoring investment | RETROFIT: installation scope, documented target and source. |
| High CAPEX | Complete equipment replacement or major line/transport redesign | REPLACEMENT: supplier or measured MTBF/MTTR targets; speed may remain unchanged. |

Intervention scope defines category; OEE gain does not. Increase MTBF, reduce MTTR. A high-investment project can have limited dynamic benefit. No monetary category thresholds, costs or ROI are invented. Capacity changes above installed maxima, reference-machine capacity changes and parallel branches remain outside the current scenario contract.

## Evidence recorded for process review

Evaluations retain category inclusions and the exact requested targets, run signatures and seeds. `phaseAudit` records baseline source, exploration counts/coverage, DOE completeness, finalist count/run and independent confirmation. These records explain what actually ran; the screen percentage reaching 100% does not certify global optimality.

## Demo B experiments

Demo B remains only a repository fixture imported from the photographs. Run `node scripts/test-demo-b.mjs --composition` for an isolated High search followed by High including Zero/Medium with a two-factor DOE. The controlled budget is twelve candidates. Use the phase evidence to decide whether additional finalists, longer exploration or interaction-preserving proposals are warranted, instead of changing outputs to reach an expected OEE.

## Reliability implementation and limits

`SCENARIO_DEFINITIONS` and `SCENARIO_INTERVENTIONS` are exported to browser and server; Gemini receives them even with user prompt overrides. Category validation rejects mismatched reliability intervention types and sensitivity-only proposals. Reliability metadata survives DOE design points, combined-category origin and server normalization. Old reliability targets lacking a type or nonempty justification must be reviewed and re-entered; their values are not silently attributed to a retrofit or replacement.

Gemini context now carries complete result provenance and replication equipment statistics into the planner. Compatible loss diagnosis uses replication means; stale/incomplete results cannot drive priorities. Observed failures and propagated starvation/blocking suggest investigation but do not prove causal lost production. Reliability availability is an equipment diagnostic, not a line OEE prediction.

Run `node scripts/test-demo-b.mjs --reliability` to generate `docs/demo-b-reliability-results.json`. The report separately evaluates per-machine sensitivity and all-machine joint sensitivity and independently checks eight-hour production using a new seed block. These exploratory levels are not supplier specifications, feasible replacement targets or guaranteed plant results. A 30-minute screen can still differ from a full shift, especially with long conveyors and slow initial filling. Threads and worker allocation are unchanged in this implementation.

### Demo B reliability sensitivity result

With thirty-minute screening and independent eight-hour / three-round checks, halving Sleever MTTR changed OEE from 39.707188% to 42.411992% (+2.704804 pp), and throughput from 76.634873 to 81.855144 units/min. Jointly doubling MTBF and halving MTTR for all seven machines yielded 71.696241% OEE (+31.989053 pp) and 138.373745 units/min in the independent check. This joint result demonstrates modeled reliability leverage, not the result of a defined replacement project. Feasible intervention targets and costs must be collected before optimization or investment selection. Thirty-minute screening baseline was 30.181858%: startup/horizon effects remain visible, so comparisons must use the matching baseline for each phase.

## Model 0.13.0: reproducible experiments

Failure, microstop occurrence and microstop duration each use an independent deterministic stream keyed by the run seed and equipment ID. Changing draws for one machine no longer consumes random numbers assigned to another machine. Physical propagation and operating-state timing can still change outcomes. IDs remain part of the experiment. Cache and scenario signatures were versioned so old measurements cannot be reused under the new random-stream policy. Old stored results may be viewed as history; rerun them before comparison with model 0.13.0. Prepared Demo results were recalculated (50.19%, 53.88%, 65.01%, 80.49%); earlier numeric results in this document are historical model-0.12.0 experiments.

The configuration dialog includes Compare experiment between computers. Capture on each computer, paste the other configuration, and compare. Exact JSON comparison reports the first mismatched field and includes model version, normalized run/seeds, equipment, selected targets, factor levels, category flags, search limits and diagnostic priorities. Concurrency is deliberately excluded. Identical settings do not guarantee plant validity; differences identify experiments that cannot be compared as exact reproductions.

Evaluate reliability sensitivity remains a diagnostic: MTBF doubles mean time between failures; MTTR halves mean repair time; JOINT does both for a machine. Its table reports differences against the matching screening baseline, in units/min and OEE percentage points. Independent checks use the configured horizon and new seeds. Values are not additive across rows. Negative or inconsistent effects need investigation; do not infer that maintenance is harmful. Results inform the user and Gemini, but search inputs change only after a documented intervention target is added.

## Diagnóstico del flujo sin fallas MTBF/MTTR

Settings → Simulation permite activar o desactivar **Enable failures and repairs (MTBF / MTTR)** para la simulación seleccionada. El valor predeterminado sigue activo; `dynamicConfig.reliabilityEnabled: false` desactiva las fallas aleatorias y sus reparaciones, conservando los parámetros del equipo. No es un objetivo de mantenimiento ni una predicción de disponibilidad real.

La opción se aplica al motor actual, al adaptador DES, a todas las rondas y a la búsqueda CAPEX. Al cambiarla se borran los resultados base visibles y la firma de entrada invalida la reutilización de mediciones incompatibles. Las propuestas guardadas siguen sujetas a su firma de origen. No se incluyen intervenciones MTBF/MTTR ni su evaluación de sensibilidad mientras las fallas están desactivadas.

| Paso | Acción | Propósito |
|---|---|---|
| 1 | Simular con fallas desactivadas y conservar la configuración física. | Identificar el rendimiento alcanzable con las pérdidas de flujo, arranque y microparos actuales. No se fuerza OEE a 100%. |
| 2 | Buscar ajustes CAPEX bajo esa misma opción. | Evaluar velocidades, sensores, reinicios y acumulación sin atribuir sus ganancias a cambios de confiabilidad. |
| 3 | Volver a activar fallas y repetir con semillas y horizontes comparables. | Verificar si las mejoras de flujo mantienen su beneficio con fallas reales modeladas. |
| 4 | Evaluar sensibilidad de confiabilidad y añadir objetivos documentados. | Separar el potencial diagnóstico de una intervención operativa, retrofit o reemplazo factible. |

Una línea sin fallas puede seguir por debajo del 100% por velocidades relativas a la referencia, falta de producto, bloqueo, arranque, rampas, microparos o comandos de paro. El resultado permite decidir qué mecanismos investigar; no constituye por sí solo una descomposición causal de pérdidas.

La sección de comparación de experimentos entre computadoras se retiró de la interfaz. Se conserva la configuración del experimento en la evidencia interna de búsqueda para trazabilidad.

## Diagnóstico de capacidad y reemplazos High CAPEX

Results y What-If muestran **Efficiency diagnosis**. El techo nominal es `min(100, 100 × velocidad mínima de las máquinas / velocidad de referencia)`. El balance muestra eficiencia lograda, brecha nominal respecto a 100% y pérdida restante debajo del techo. Con varias rondas, usa el OEE medio. El techo no incluye límites de transporte ni pérdidas dinámicas; el residual no se distribuye por causas sin experimentos adicionales. La tabla de tiempos observados por equipo usa porcentajes de duración y medias de réplicas disponibles: estos porcentajes pueden superponerse y no son contribuciones aditivas al OEE global. DES experimental no presenta este balance como OEE validado.

En **Add maintenance, retrofit or replacement target**, seleccionar **Replacement operating speed (units/min)** y un equipo no crítico. Introducir velocidad de operación, nueva capacidad máxima instalada y justificación/fuente del objetivo. El máximo debe aumentar, la operación no debe excederlo y la referencia queda fija. El cambio nominal lleva `replacementMaximumBpm`, `external:true`, `interventionType:REPLACEMENT` y `justification`: la aplicación cambia operación y máximo de manera conjunta. La categoría permitida es High; también funciona con fallas desactivadas. DOE y el servicio de creación conservan los metadatos. Se conservan geometría y topología actuales; no se asume que el proveedor garantiza compatibilidad con ellas.

El planificador prioriza los reemplazos documentados de las máquinas que limitan el techo nominal. La búsqueda evalúa cambios individuales y combinaciones con sus controles existentes, conserva el diagnóstico inicial y registra el techo y limitante finales. No inventa una compra, capacidad ni costo. Los desbordamientos observados durante la búsqueda o confirmación generan revisión de ingeniería aunque aumente el throughput; las mediciones antiguas sin este dato se recalculan.

Prueba reproducible: `node scripts/test-demo-b-capacity.mjs`. Demo B, ocho horas, fallas desactivadas, referencia Blowmolder 193/min, geometría de fotos conservada, una ronda diagnóstica por caso. Valores hipotéticos de reemplazo: operación 200/min y máximo nuevo 220/min; no son especificaciones de proveedor.

## Cobertura de propuestas y lectura del resultado DOE

El planificador devuelve `proposalNeeds` y What-If muestra **Missing intervention targets** antes de las tarjetas. Separa restricciones de capacidad nominal sin reemplazo documentado y oportunidades de confiabilidad sin objetivo de intervención válido. La disponibilidad `MTBF / (MTBF + MTTR)` y la capacidad nominal multiplicada por disponibilidad son filtros de investigación, no una predicción del throughput ni prueba de causalidad. Los objetivos inválidos o sin fuente no cubren una necesidad. Gemini recibe este inventario acotado.

Demo B importado, sin objetivos adicionales, contiene cinco máquinas no críticas con máximo instalado inferior a la referencia 193/min. Con fallas activas, De-Pucker y Sleever aparecen primero por su disponibilidad intrínseca de 71.4286% y capacidad orientativa 132.1429/min. Esto explica por qué una búsqueda de sensores y buffers puede ofrecer una mejora mínima sin abarcar las inversiones de confiabilidad o capacidad de mayor alcance. El 99.117886% del experimento anterior necesitó cinco objetivos hipotéticos explícitos; no era el resultado automático del planificador.

Suggest factor combination distingue `NO_GAIN_IN_TESTED_TARGETS`, `POSITIVE_BUT_UNSTABLE`, `GAINS_REQUIRE_ENGINEERING_REVIEW` y `STABLE_FACTORS_FOUND`. La ausencia de sugerencias conserva la selección manual y no impide calcular un DOE con factores y niveles válidos. No demuestra que no existan interacciones de orden mayor o intervenciones fuera del espacio evaluado.

El flujo de revisión queda: diagnóstico de mecanismo → identificación de intervención/objetivo faltante → pruebas aisladas y conjuntos por mecanismo → selección DOE dentro de objetivos factibles → comparación de finalistas con horizonte representativo → confirmación independiente. Los tiempos por equipo no se suman como pérdidas globales; los niveles de sensibilidad no se convierten automáticamente en objetivos de compra. Al desactivar fallas, la cobertura MTTR para absorción de paros queda no evaluada, sin imponer una duración de reparación a la hipótesis de buffer.

## Búsqueda inversa de objetivos de confiabilidad (exploratoria)

High CAPEX incorpora **Explore MTBF / MTTR targets before High CAPEX search**, activo por defecto con fallas activadas. Profundidad Light lo omite; Medium y High lo ejecutan. Desactivarlo mantiene la búsqueda de objetivos suministrados. El algoritmo no modifica el caso original ni añade sus objetivos a `externalOptions` como intervenciones documentadas.

1. Comparar la base con todas las fallas MTBF/MTTR desactivadas y con las fallas de cada máquina desactivadas por separado. Mantener velocidades, geometría, microparos, horizonte y semillas. Se examinan hasta 12 máquinas y se declara la cobertura. Las ganancias por equipo son diferencias condicionales y se superponen; no se suman ni constituyen un Pareto causal de OEE.
2. Priorizar hasta tres máquinas en profundidad High (dos en Medium). Explorar MTBF, MTTR y ambos, con grados `(×1.25, ×0.8)`, `(×1.5, ×2/3)`, `(×2, ×0.5)` y `(×4, ×0.25)`. MTBF siempre aumenta y MTTR disminuye; mantener límites numéricos positivos del modelo. Los objetivos no son especificaciones de mantenimiento o proveedor.
3. Para cada equipo, preferir el menor cambio relativo de parámetros que recupera al menos 90% de la mejor ganancia aislada probada. Es una heurística de exigencia de parámetros, no costo o ROI. Preferir alternativas sin alertas; conservar hipótesis con alertas para revisión si no hay alternativas admisibles. Probar paquetes conjuntos y grados conjuntos para descubrir interacciones que no se ven en pruebas aisladas.
4. Incorporar paquetes y coordenadas exploratorias a la búsqueda. Los objetivos suministrados seleccionados prevalecen sobre duplicados automáticos. Evaluar controles y geometría también en el contexto de los objetivos de confiabilidad, para investigar desbordamiento y recuperación.
5. Si DOE está activo y no hay factores manuales, examinar hasta ocho objetivos de flujo con seis semillas emparejadas y confiabilidad fija. Seleccionar ganancias estables sin aumentar el desbordamiento del contexto y ejecutar DOE/ANOVA condicional. Si no hay factores estables, continuar sin DOE y explicar el motivo. Los factores manuales se conservan.
6. Confirmar el candidato contra la base con horizonte completo y semillas independientes, ampliando a seis rondas si High es incierto. Exigir estabilidad de la confirmación, además de ganancia media. En el mismo bloque, medir también la base sin fallas para el balance de pérdida condicional de confiabilidad. Los resultados anteriores se conservan como historia pero requieren volver a evaluar con la política `RELIABILITY_TARGETS_V6`.
7. Cuando no hay mejora, no mostrar un candidato inferior como mejor escenario. Cuando falla la confirmación, el encabezado conserva la base y el detalle permite inspeccionar el candidato fallido. Mostrar siempre la base emparejada con el escenario.

Los cambios automáticos usan `analysisOnly:true` e `interventionType:SENSITIVITY`. Solo pueden crearse mediante una propuesta explícita `analysisOnly:true`. La simulación guardada conserva `classification:UNASSIGNED`, `capex:null`, `plantValidated:false` y estado de revisión de factibilidad. El objetivo puede investigarse antes de disponer de información de proveedor, pero no se presenta como intervención High CAPEX aprobada. La categoría real se determina posteriormente al identificar mantenimiento, retrofit o reemplazo.

Results muestra un balance adicional correspondiente al bloque emparejado de validación: eficiencia base + diferencia condicional al desactivar fallas + brecha nominal por velocidades + pérdida restante sin fallas = 100 pp. El término de confiabilidad incluye efectos propagados sobre el flujo. Los porcentajes de tiempo por equipo siguen siendo observaciones superpuestas y no se añaden a este balance.

El ranking inicial fue De-Pucker, Sleever y Filler/Capper. Objetivos seleccionados: MTBF 5→20 min en De-Pucker/Sleever y 10→40 min en Filler; MTTR 2→0.5 min en los tres. ## Equipment scope and engineering limits (V7)

High configuration now saves `whatIf.reliabilitySettings` with AUTO, MANUAL or ALL scope. AUTO screens up to twelve machines and prioritizes the configured number (default three). MANUAL screens and explores every checked eligible machine, including those without a positive isolated failure-removal gain, and joint packages. ALL removes the twelve-machine screening cap and explores every eligible machine. Larger scopes cost more simulation time; this is a bounded search, not an exhaustive search over every subset. Manual scope excludes reliability targets and DOE factors for unchecked machines; flow improvements remain eligible across the line.

Each machine accepts an optional MTBF maximum, MTTR minimum and source/basis. MTBF maximum must be at least the current MTBF; MTTR minimum must be positive (at least 0.001 min) and no greater than current MTTR. Exploratory grades are clipped to these bounds. Supplied targets, coordinate trials, DOE treatments and independent confirmation cannot bypass them. Empty bounds preserve the former relative exploratory levels and do not establish engineering feasibility. Bounds and source are retained in configuration, discovery evidence and the experiment signature; edits invalidate earlier results. Known supplier targets remain available through Add intervention target, with automatic exploration disabled if desired. The configured equipment count is not a monetary budget or a promise that every chosen machine will be changed in the winner. Selection limits which machines may change; it does not force a beneficial replacement. Changing scope or bounds requires reevaluation under RELIABILITY_TARGETS_V7.

## Conditional DOE / ANOVA optimization (V8)

The suggestion button and automatic High/Medium factor selection now call one shared `screenFlowFactors` implementation. In High, inverse reliability targets (when enabled) are prepared first; selected supplied targets override automatic duplicates. The exact discovery configuration and completed report are reused while source signature, run and equipment settings match. Flow-screen reports also reuse exact source/context/targets/run signatures. Changed inputs, scope, limits, levels or engine policy require reevaluation; no approximate match authorizes a scenario.

For unedited planner targets, engineering hypotheses are refreshed with the retained MTBF/MTTR context. V-Graph recommended operating speed becomes the tested target, bounded by installed maxima and the user's field limit. Explicitly edited targets win. Zero speed adjustments enter High only when the user includes Zero; documented High capacity replacements remain eligible in High. Missing replacement capacities are still reported as required inputs, not invented. Up to three speed hypotheses have reserved shortlist slots, within eight total targets. The evidence table shows current/tested speed, installed or replacement maximum, throughput gain and intervention scope. A recommendation is a test level, not a demonstrated production benefit.

The shared screen uses the depth exploration horizon (Medium ten minutes, High fifteen), three matched seeds per baseline/single/pair, up to eight targets and six prioritized physical-neighbor pairs. Uncertain intervals with admissible engineering checks receive three distinct additional seeds; the extra baseline is reused and the first block is not repeated. Clear no-gain trials remain screened out provisionally. Stable three-seed results may qualify for DOE, but do not replace final independent confirmation. Short screening can miss long-buffer recovery or higher-order interactions; reports disclose omissions and uncertainty. Six-seed extension records both seed blocks.

Automatic DOE selects at most three factors: at most eight factorial combinations, with seed-block ANOVA for High. The user's edited/manual four-factor selection remains supported. With automatic DOE, inverse-search reliability objectives remain fixed, coordinate refinement uses one pass and a cap of 48 candidates (or a smaller explicit override). When factors qualify, ordinary refinement explores that shortlist; it does not silently continue across every eligible field. If no factors qualify, a capped ordinary flow search continues without claiming that no further improvement exists. The full configured horizon and independent seeds are retained for final confirmation. The factorial DOE and ANOVA are conditional on the retained reliability context; selected factors do not claim additive causal loss shares or plant statistical significance.

Controlled checks: `node scripts/test-demo-b-flow-screening.mjs` measures the isolated screen with previously measured reliability targets. `node scripts/test-demo-b-conditional-search.mjs` checks a twelve-candidate all-category search and the independent eight-hour confirmation, also reusing the previously measured inverse-search report. These scripts report their exact tested scope and are not an exhaustive investment search. The suite includes coupled-only gains, adaptive seed extension, cache reuse between button and search, engineering overflow checks, speed refresh and manual factor preservation.

Controlled Demo B result for V8: the isolated eight-target/six-pair screen used twenty three-round batches including uncertainty extensions and selected no stable factors at the tested horizon. The twelve-candidate all-category search therefore continued without factorial DOE. Independent eight-hour / three-seed confirmation measured 39.466840% baseline and 67.472299% candidate OEE; gain reproduced, with simulated overflow requiring engineering review. This result checks the fallback and confirmation path; it does not demonstrate complete factorial coverage or a globally best scenario. Fifty-one focused tests passed, including complete manual four-factor DOE/ANOVA. Three legacy interface-test failures were reproduced unchanged on the previous d1da7f1 version; the broader suite was not claimed as passing.

## Compact scenario presentation

Results presents conditional reliability loss, nominal speed gap and remaining failure-free loss as KPI cards. Missing failure-free evidence remains unavailable; observed equipment/state percentages are displayed in descending order and retain the overlap note. What-If opens with CAPEX cards; the standalone sensitivity panel and introductory diagnosis panels are removed. The shared target editor is available inside the equipment/input configuration section. Configuration has three tabs: Search (depth, DOE and category options), Equipment, and Conveyors. Live cards reserve minimum space for metrics, status, warnings and progress; content grows without internal scrollbars and all cards share the tallest height. Warnings open on request. Scenario results list numeric inputs and considered-equipment MTBF/MTTR values, including installed maximum speed where applicable, without prescribing maintenance or replacement actions. These are presentation changes; search calculations, saved evidence and engineering-review state are retained.

## Matched Results loss values and configuration tabs

Results now calculates the unchanged simulation without reliability failures using the completed result's exact equipment/run provenance, horizon and seeds. It uses the displayed batch-mean OEE as the baseline, waits for any current calculation to finish, and stores the completed compact diagnostic in the simulation's What-If data. Exact-key matches reuse it. Pending/interrupted results do not launch this calculation; experimental SimPy remains excluded. Values display percent of the reference capacity: achieved OEE + conditional reliability loss + nominal speed gap + remaining failure-free loss = 100%. The three losses alone total 100% minus OEE. Observed-state percentages use the standard scrollable table with semantic headings, numeric alignment and descending ordering.

Scenario configuration has a three-button tab list with roving keyboard focus and one visible panel, in the same fixed-height dialog pattern as Settings.
